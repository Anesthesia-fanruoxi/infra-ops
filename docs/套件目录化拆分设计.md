# 套件目录化拆分设计

- 状态：**已定稿**（议题 ①②③④ **全部拍板**，可按 §8 分期实施）
- 日期：2026-09-14（决策更新：2026-09-14）
- 决策纪要：① 套件 Go 代码与 `scripts/` **同级**（方案 A）；② 前端**静态引入**（方案 A）；③ **一次性迁移全部 9 套件**；④ 部署模板体系**不纳入**本次目录化（仅做 embed 最小联动）。详见 §12。
- 范围：套件（Stack）的后端执行/探活逻辑、前端组件与样式的**目录化拆分**
- 关联文档：`docs/角色物化设计.md`、`docs/ES套件冷热温架构设计.md`、`docs/大数据底座套件设计.md`、`docs/大数据底座高可用设计.md`
- 关联规约：`workflow/boundaries/rules.md`（单文件尽量不超过 500 行）

## 1. 背景与目标

### 1.1 用户诉求（原话拆解）

1. 套件逻辑过于复杂，**全部拆分开**。
2. 后端：套件的**执行逻辑**与**探活逻辑**单独写进 `store/stacks/<套件>/` 目录；**通用入口仍留在 `store/builtin_stacks.go`**。
3. 前端：同样建套件目录，**通用逻辑抽为公共组件**，每个套件的 js / css 存于自己的套件目录。
4. 收益预期：**各套件展示效果可以不一样**；修改时**不会互相冲突**。

### 1.2 目标（可验收）

| 维度 | 现状 | 目标 |
|------|------|------|
| 新增一个套件 | 改动 ~15 个引擎文件、40+ 处 `if bp.Key == "xxx"` | **新增 1 个目录 + 2 处注册（后端 1 行、前端 2 行）** |
| 改动一个套件 | 需在跨套件共享文件中定位分支，易误伤他人 | **只改本套件目录，物理隔离** |
| 前端样式 | 全站单一 `style.css`，套件样式与大类名混排 | **每套件一份 css，前缀命名空间隔离** |
| 单文件规模 | `stacks.js` 1824 行、`style.css` 2333 行，远超 500 行规约 | 全部文件 ≤ 500 行 |
| 代码归属 | 套件行为分散在引擎里，读一个套件要跳十几个文件 | 一个套件的行为**在一个目录内读得完** |

### 1.3 明确不做（本次范围外）

- 不改任何 bash 脚本内容（`scripts/*.sh` 原样移动/复用，逻辑零变更）。
- 不改对外 HTTP API 契约、不改数据库 schema。
- 不引入前端构建链（webpack / vite / 打包器一律不引入）。
- 不做前端按需加载（§5.4 方案 B 列为后续可选优化）。
- 不做套件功能的增删改（本设计是**纯结构重构**，行为必须逐字节等价）。
- **不改造部署模板体系**（`store/builtin_templates.go` 的约 30 条模板定义保持原样，见议题④）；只同步其 `go:embed` 声明与脚本读取入口，使其不再把套件 `.go` 打进二进制。

## 3. 问题解剖（为什么现在必须拆）

1. **开关地狱**：套件身份用 `bp.Key == "xxx"` 字符串判断，散在 15 个文件里。新增套件时无法通过编译器发现遗漏点，漏一处就是运行期行为错乱（如 ELFK 第一次接入时，`registerStackService`、`planGenericRoles`、`stackClusterExtra` 三处都要改）。
2. **读不全一个套件**：理解「冷热温缩容为什么拦得住」要同时读 `stack_instance_validate.go`、`stack_create_hosts.go`、`stack_plan_generic.go`、`stack_op.go`、`stack_phase.go` 五个文件。
3. **改动互相踩**：`stacks.js` 与 `style.css` 是全局共享，两个套件同时改必然冲突；ES 的 138 条 `.es-*` 样式挤占全站样式表。
4. **展示效果雷同**：前端只有一个渲染路径，套件差异化只能靠 `v-if` 打补丁，无法做出「ES 有角色分层表 / bigdata 有组件矩阵 / redis 有拓扑选择」这种真正的形态差异。
5. **行数失控**：`stacks.js` 1824 行、`style.css` 2333 行，均超规约 3–5 倍，已丧失可维护性。

## 5. 关键设计

### 5.1 套件驱动契约：最小接口 + 可选能力

避免「每个套件实现 20 个方法」的模板地狱，采用**最小必选 + 能力断言**两段式。

**（1）必选契约 `stackkit.Driver`**（每个套件都实现，约 40 行样板）：

```go
package stackkit

type PhaseFile struct {
    Path   string            // 相对 store 包：stacks/<key>/scripts/xxx.sh
    Assets map[string]string // @@KEY@@ -> stacks/<key>/configs/xxx
}

type Driver interface {
    Key() string
    Blueprint() model.StackBlueprint
    Phase(mode, phase string) (PhaseFile, bool) // phase: node / bootstrap / scale_out / scale_in
    Pipeline(mode string) []model.StackPhase    // 空 = 走传统 node→bootstrap 单步
}
```

**（2）可选能力接口**（引擎用类型断言调用，未实现即走通用默认）：

| 接口 | 方法 | 替代现状 | 首批迁移对象 |
|------|------|---------|-------------|
| `RolePlanner` | `PlanRoles(PlanInput) (model.RolePlan, error)` | `planGenericRoles` 的 switch | 全部 9 套件 |
| `ServiceRegistrar` | `RegisterServices(RegisterCtx)` | `registerStackService` 的 key 特判 | bigdata / es / elfk / kafka |
| `VarInjector` | `ExtraVars(VarsCtx) map[string]string` | `stackClusterExtra` / `stackCWHExtraMerged` / `bigdataMasterExtra` | es / bigdata / elfk |
| `CreateValidator` | `ValidateCreate(ValidateCtx) error` | `stack_create.go` 的 88–125 | redis / es / bigdata / kafka / rabbitmq |
| `ScaleGuard` | `ScaleGuard(ScaleCtx) error` | `stack_instance_validate.go` 41–53 | redis / bigdata / es |
| `TopologyBuilder` | `ValidateTopology(TopoCtx) error` ⚠️实施期修订 | `stack_topo.go` | redis |
| `DefaultsProvider` | `Defaults(mode string, params map[string]string)` | `stack_create.go` 默认值注入 | kafka / rabbitmq / redis / es |
| `VerifyProbe` | `VerifyScript(VarsCtx) string` / `ParseVerify(raw string) []Endpoint` | `stack_verify_script.go` / `stack_verify_redis.go` | redis / bigdata / es |

**（3）角色规划助手**（把现有 case 几乎原样搬移）：

```go
// stackkit/plan_helper.go
type Roles struct {           // 引擎构造，套件消费
    Boot model.StackRunHost
    Rest []model.StackRunHost
    All  []model.StackRunHost
}
func (r *Roles) AddAt(comp, role, label, scope, source string, h model.StackRunHost)
func (r *Roles) AddAll(comp, role, label string)   // scope=all
func (r *Roles) AddRest(comp, role, label string)  // scope=rest
func (r *Roles) Warn(format string, a ...any)
```

迁移后 `elasticsearch/plan.go` 示例：

```go
func (d *esDriver) PlanRoles(in stackkit.PlanInput) (model.RolePlan, error) {
    plan := in.NewPlan()
    switch in.Mode {
    case "cluster":
        in.Roles.AddAt("elasticsearch", "boot_master", "引导主节点（master, data）", "", in.Src(), in.Roles.Boot)
        in.Roles.AddRest("elasticsearch", "data", "数据节点（data）")
    case "cold_warm_hot":
        // 原冷热温分层逻辑原样搬入
    }
    return plan, nil
}
```

### 5.2 通用入口保留什么（`store/builtin_stacks.go` 的最终形态）

保留（通用，与套件无关）：

- `FindBuiltinStack(key)` → 改为返回 `stackkit.Driver`（迁移期用兼容壳，见 §8 P1）
- `ModeDef(mode)` / `Blueprint()` / `LoadPhase(mode, phase)` 的**渲染实现**（读 embed + `@@ASSET@@` 替换）
- `Pipeline(mode)` 转发
- `DockerTemplateName` 常量

移出（套件专属）：

- 全部 9 个 `BuiltinStack{...}`（P1 后为 `legacyStack{...}`）蓝图字面量 → 各套件 `Blueprint()`
- `bigdataMasterVars` / `bigdataSecondaryVars` / `bigdataRoleKeys` → `store/stacks/bigdata/`

目标：`store/builtin_stacks.go` **降到 120 行以内**，只剩「查 + 渲染 + 转发」。

> **P7（B10）落地修订**：上面「保留」清单是**迁移期**形态。删壳后的终态只留一个包级函数
> `LoadStackPhase(d, mode, phase)`；`ModeDef` 下沉为 `stackkit.ModeDef(bp, mode)`；
> `Blueprint()` / `Pipeline()` 由驱动直接实现，**转发面归零**（壳不再持有 `drv` 字段，转发无处安放）。
> 详见 §13 的 P7 行。

### 5.3 `go:embed` 收紧（**已定稿**：方案 A，Go 代码与 `scripts/` 同级）

套件目录内出现 `.go` 后，`//go:embed stacks` 会把它们当静态资源一起打包。改法：

```go
// store/embed.go（新建，唯一 embed 声明点）
//go:embed stacks/*/scripts stacks/*/configs
var StackFS embed.FS

//go:embed builtin
var BuiltinFS embed.FS
```

要点与验证：

1. `//go:embed` 的**目录模式是递归的**，`stacks/*/scripts` 会包含 `stacks/elasticsearch/scripts/cold-warm-hot/node.sh` 这类三级路径 ✅
2. **FS 内路径保留完整相对路径**，`StackFS.ReadFile("stacks/redis/scripts/node.sh")` 行为不变 ✅
3. 无 `configs/` 的套件（kafka / elfk / powerjob）只是该模式项不匹配，不影响编译 ✅
4. **`store/builtin_templates.go:13` 的联动（即原「待拍板事项④」的技术根源）**：它当前是 `//go:embed builtin stacks/elasticsearch stacks/rocketmq stacks/rabbitmq`，会连带把这三个套件目录下的 `.go` 一并打进二进制；故必须同步收紧为 `//go:embed builtin stacks/*/scripts stacks/*/configs`，并把模板中 3 处**直接指向套件脚本**的路径（`stacks/rocketmq/scripts/namesrv.sh`、`stacks/rocketmq/scripts/broker.sh`、`stacks/rabbitmq/scripts/node.sh`）改走统一 `StackFS` 读取（`BuiltinFS` 与 `StackFS` 可共存于 `store/embed.go`）。**注意：此处只改「embed 声明 + 读文件入口」，不迁 `builtinTemplates` 的 30 条模板定义（**议题④已拍板**：模板体系不纳入目录化）。**
5. **新增启动自检 + 单测**：遍历 registry，对每个套件的每个 mode 调 `Phase("node")`，读不到即 fail。这把「embed 模式写错」从运行期问题变成启动期/测试期问题

### 5.4 前端加载与样式隔离（**已定稿**：采用方案 A 静态引入）

**方案 A（已拍板）：静态引入 + 目录分组**

`index.html` 保持静态 `<script>` / `<link>`，按套件分组并加注释：

```html
<!-- 套件：通用骨架 -->
<script src="/static/stacks/registry.js"></script>
<script src="/static/stacks/common/wizard.js"></script>
<link  rel="stylesheet" href="/static/stacks/common/common.css">
<!-- 套件：Redis -->
<script src="/static/stacks/redis/index.js"></script>
<script src="/static/stacks/redis/topo.js"></script>
<link  rel="stylesheet" href="/static/stacks/redis/style.css">
<!-- 套件：大数据底座 -->
...
```

- 优点：**零加载时序风险**、`go:embed` 一次性打包、无构建链、内网首屏成本可忽略（每套件 css 通常 < 8KB）。
- 满足诉求：物理隔离 ✅、可独立改 ✅、展示效果可不同 ✅。

**方案 B（后续可选）：运行时按需注入**

`loadStackAssets(key)` 在进入向导时注入 `link` + `script`。收益是首屏更小；代价是 Vue 组件注册时序竞态、调试复杂度、离线校验变难。**已拍板：本次不采用**（议题②取方案 A），待套件数超过 15 个再评估。

**样式命名空间约定**（强制）：

- 通用：`.stk-*`（wizard / host-table / role-plan / instance-card）
- 套件：`.stk-<key简写>-*`，如 `.stk-es-role-chip`、`.stk-bd-comp-card`、`.stk-redis-topo`
- 现存 `.es-*`（ES 控制台，9 个 `es_*.js` 已自洽）**不动**；`stacks` 的 ES 专属样式改用 `.stk-es-*` 以区分

### 5.5 「通用 vs 独有」判定准则（三问）

1. **只有 1 个套件需要？** → 放该套件目录。
2. **≥2 个套件需要，且语义完全相同？** → 抽到 `stackkit` / `common`。
3. **拿不准？** → 先放套件目录；**第二次出现复用需求时再上提**（禁止过早抽象）。

### 12.1 议题④释义（原描述到底在问什么）

`store/builtin_templates.go` 与套件（stacks）**是两个不同的产品概念**，本不该混说：

- **套件（stacks）**：面向**多台主机**的集群编排，链路是 角色规划 → pipeline 阶段调度 → 服务登记 → 链路校验。**这才是本设计要目录化的对象。**
- **部署模板（builtin_templates）**：面向**单台主机**的「基础建设」应用部署模板（约 30 条：MySQL / Redis / MongoDB / Kafka / ClickHouse / MinIO …）。它在启动时由 `seedBuiltinTemplates()` 把脚本与元数据**写进数据库** `deploy_templates` 表，供「部署任务 / 定时任务」引用；**不参与角色规划，也不走 pipeline 编排。**

两者本应互不相干，但在**文件层面有一处耦合**：其中 3 条模板的脚本路径**直接指向套件目录**——

| 模板名 | 脚本路径 | 所属套件 |
|--------|---------|---------|
| 部署 RocketMQ NameServer | `stacks/rocketmq/scripts/namesrv.sh` | rocketmq |
| 部署 RocketMQ Broker 节点 | `stacks/rocketmq/scripts/broker.sh` | rocketmq |
| 部署 RabbitMQ 集群节点 | `stacks/rabbitmq/scripts/node.sh` | rabbitmq |

因此议题④真正要问的是：**在这次拆分里，要不要顺手把 `builtin_templates.go` 也改成 `store/builtin/<name>/` 那样的目录化结构（与套件同构）？**

> 需要强调：**无论④怎么选，`builtin_templates.go` 的 embed 声明都一定要改**（因为议题①=A 的 embed 收紧会让它继续把套件 `.go` 打进二进制）。④ 决定的是「要不要连 30 条模板定义一起搬家」。

### 12.2 议题④的选项与推荐

| 选项 | 内容 | 收益 | 代价 |
|------|------|------|------|
| **④-A 同批目录化** | 30 条模板定义也拆进 `store/builtin/templates/<name>/`（每条一个目录：元数据 + 脚本 + 资源） | 两套体系结构完全统一，`builtin_templates.go` 也能降为薄壳 | 30 条模板 × 元数据搬迁，工作量大；与套件拆分**同期叠加风险**；且模板体系当前并没有「分支地狱 / 行数失控」问题，收益有限 |
| **④-B 不同批（已采纳）** | **只做最小必要改动**：embed 收紧 + 3 处套件脚本路径改走统一 `StackFS` 读取；`builtinTemplates` 的 30 条定义**原样保留** | 保证 §5.3 的 embed 收紧到位（否则套件 `.go` 仍会被打进二进制）；风险最小、范围不扩张 | 模板体系的结构债留待独立任务处理 |

**采纳 ④-B（已拍板）**。理由：议题④之所以被列出，本质是「①=A 的 embed 收紧**必须**动到它」，**而不是**「它自己有拆分需求」。既然本次是「纯结构重构、不做功能增删」，把 30 条模板定义一并搬家属于**范围外扩张**，与「每期只搬不改、可独立回滚」的迁移原则相悖。

需求方补充判断依据：**模板体系由单个 shell 脚本构成，逻辑简单**（无多阶段编排、无角色规划、无跨机协同），不存在套件那种「分支地狱 + 行数失控」的复杂度，目录化收益不抵搬迁成本。**结论：本次不动其结构；若未来模板数量或复杂度显著上升，再另立文档单独评估。**

> 备查（未采纳路径）：若未来启用 ④-A，§8 需新增一期 **P4.5「模板体系目录化」**，且 P0 基线需额外覆盖约 30 条模板的 seed 产物（`deploy_templates` 表快照），否则无法验证搬迁前后 seed 结果一致。
