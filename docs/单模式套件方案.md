# 单模式套件方案（nacos / rabbitmq / rocketmq / powerjob）

> 背景：redis / kafka / elasticsearch 三个**多模式**套件已收口。剩下 4 个**单模式 `cluster`** 套件。
> 它们的共同形态是：**只有一枚 `node.sh`，没有 bootstrap / scale_in / scale_out 阶段**
> （`baseline/render/` 里 4 套件 × 3 阶段全部是 `NO_SCRIPT`），
> 因此能力缺口与硬缺陷的形态也高度一致——可以一次盘清、分批改造。
>
> 盘点方法沿用 `docs/新增套件说明.md`：先解析**三张表**（模式 / 角色 / 步骤），
> 再对照 `store/stackkit/capability.go` 与 `probe.go` 的**能力接口矩阵**。

---

## 1. 第一张表：模式表（4 套件并排）

| 套件 | 模式 key | Label | MinHosts | AssignMaster | HasBootstrap | 默认主目录 |
|---|---|---|---|---|---|---|
| nacos | `cluster` | 集群 | 1 | ✅ | ✗ | `/data/nacos` |
| rabbitmq | `cluster` | 集群 | 1 | ✅ | ✗ | `/data/rabbitmq` |
| rocketmq | `cluster` | 一步成型 | 1 | ✅ | ✗ | `/data/rocketmq` |
| powerjob | `cluster` | 集群 | 1 | ✅ | ✗ | `/data/powerjob` |

四个都是「1 引导节点 + N 成员」的同构拓扑，`MinHosts` 均为 1（无硬下限），全部 `AssignMaster=true`。

## 2. 第二张表：角色表

| 套件 | 落点角色（`AddAt`） | 成员角色（`AddRest`） | 运行期角色 | 落点受通用保护 |
|---|---|---|---|---|
| nacos | `boot` 引导节点（MySQL + Nacos） | `member` Nacos 成员 | master / worker | ✅ |
| rabbitmq | `seed` 初始化节点 | `member` 集群成员 | master / worker | ✅ |
| rocketmq | `master` NameServer + Broker Master | `slave` Broker Slave | master / worker | ✅ |
| powerjob | `boot` 引导节点（MySQL + Server） | `server` Server 成员 | master / worker | ✅ |

> **纪律提示（本次盘点踩过的坑）**：`stackkit.RegisterCtx.Host.Role` 是**运行期角色**
> （经 `stackHostRole` 命名：`AssignMaster=true` → `master`/`worker`），
> **不是**角色表里的 `boot` / `seed` / `slave`。
> 所以 `rabbitmq/register.go` 里 `case "master", "worker"` 是**正确**的，不是死分支——
> 一开始按角色表读会误判。以后查套件服务登记，一律以 `baseline/cases/<key>_<mode>.json`
> 的 `services[].service_name` 为准（它拿的是运行期角色）。

## 5. 硬缺陷（实现错误，不是「能力缺失」）

这一节是本次盘点的重点：**4 个套件里有 3 个存在用户可见的错报或残留**，且成因都在套件脚本自身。

### D1 探活永久假红：rocketmq / powerjob 🔴

证据链（三处代码对齐）：

1. 探活脚本只 glob 三个路径（`api/stack/stack_verify_script.go:25`）：
   ```sh
   for cf in "$HOME_DIR/compose.yml" "$HOME_DIR/docker-compose.yml" "$HOME_DIR"/*/compose.yml
   ```
2. 空 compose 块的判定（`store/stackkit/probeutil.go:99-103`）：
   ```go
   raw = strings.TrimSpace(raw)
   if raw == "" { return false, "未找到 compose 服务" }
   ```
3. 四个套件实际写的 compose 文件名：

| 套件 | 脚本里写的 compose | 命中 glob？ |
|---|---|---|
| nacos | `${HOME_DIR}/compose.yml` | ✅ |
| rabbitmq | `${HOME_DIR}/compose.yml` | ✅ |
| **powerjob** | `${HOME_DIR}/compose.yml.${SELF_ID}` | ❌ |
| **rocketmq** | `${HOME_DIR}/namesrv-compose.yml` + `${HOME_DIR}/broker-compose.yml` | ❌❌ |

→ powerjob / rocketmq 的 compose 块恒为空 ⇒ `ParseComposeStates("")` 恒返回 `(false, "未找到 compose 服务")`
⇒ **无论集群多健康，探活结果永远是失败**。（nacos 的 `mysql-compose.yml` 也不在 glob 内，boot 机的 MySQL 容器看不见，但主 compose 命中，所以整体不假红。）

### D2 卸载 / 缩容不停容器：rocketmq / powerjob（+ nacos 的 MySQL）🔴

`stackComposeDownScript(home, comps, purge)`（`api/stack/stack_compose.go:12`）在 `comps` 为空时，
目录集是**硬编码的大数据组件清单**：

```go
dirs = []string{"", "hadoop", "zookeeper", "yarn", "spark", "flink", "hive", "hbase", "trino"}
...
down_one "${HOME_DIR}/compose.yml"
down_one "${HOME_DIR}/hadoop/compose.yml" ...
```

`scale_in` / `uninstall` 走的正是 `comps == nil` 分支（`remove_components` 只在 `remove_component` op 里才有），
于是**只有 `${HOME_DIR}/compose.yml` 与那 9 个目录会被处理**：

| 套件 | `down` 是否命中 | 后果 |
|---|---|---|
| nacos | ✅ `compose.yml` | nacos 容器停了；**`mysql-compose.yml` 未命中 → MySQL 容器残留** |
| rabbitmq | ✅ `compose.yml` | 正常 |
| **powerjob** | ❌ `compose.yml.<seq>` | **容器不停，任务却报「本机套件服务已停止」** |
| **rocketmq** | ❌ 两个非标准名 | **namesrv + broker 容器全部不停** |

`purge` 同理：`rm -rf` 只删那 9 个目录 + `compose.yml` ⇒ powerjob 的 `server-<seq>`、
rocketmq 的 `store/`、nacos 的 `mysql-data/`、`data/` **全部不会被清理**。

> 与 kafka 的 K3/K4 的区别：kafka 那两个要动通用层（side-car compose / purge 目标声明能力）；
> **这四个套件不需要**——只要把 compose 文件名写回引擎认得的约定即可（见 M1/P1/N4），**零通用层改动**。

### D3 rocketmq 的接入地址在「一步成型」合并时丢失（真实回归）🟠

拆分期之前的 `api/stack_engine.go:977-983` 明确登记过：

```go
"rocketmq/namesrv": { "node":   {name: "RocketMQ NameServer", url: "rocketmq://" + ip + ":" + pick("port", "9876"),   web: false} },
"rocketmq/broker":  { "master": {name: "RocketMQ Broker 主",  url: "rocketmq://" + ip + ":" + pick("broker_port", "10911"), web: false},
                      "worker": {name: "RocketMQ Broker 从",  url: "rocketmq://" + ip + ":" + pick("broker_port", "10911"), web: false} },
```

两个模式（namesrv / broker）合并为一步成型的 `cluster` 之后，
`registry["rocketmq/cluster"]` 与 `registry["rocketmq"]` **都不存在** → 落到通用默认
`{"master": "http://"+ip, "worker": "http://"+ip}`（无端口、`web:false`）。

当前基线 `baseline/cases/rocketmq_cluster.json` 正是这个值（`"url": "http://10.0.3.1"`），
`store/stacks/rocketmq/plan.go:10` 的注释也自认「服务登记待 P3（B8）迁入本目录」——
**即：这是拆分时未完成的迁移，不是设计取舍。**

### D4 nacos / powerjob 控制台入口缺失（一直如此，非回归）🟡

拆分期前的 registry 只有 `kafka` / `elasticsearch/cluster` / `rabbitmq/cluster` / `rocketmq/*` 四条，
**nacos 与 powerjob 从来没有条目**，所以通用默认给 `http://<ip>`（无端口、`web:false`）。
而两者的真实控制台是：

- nacos：`http://<ip>:8848/nacos/`（默认账号 `nacos/nacos`）
- powerjob：`http://<ip>:7700/`（默认账号 `powerjob/powerjob123456`）

→ 平台上点不进去，只能手工拼 URL。

## 6. 缩容风险画像（逐套件）

**共同前提：4 个套件的落点角色都在通用保护范围内。**
`validateScaleIn` 先调套件 `ScaleGuard`，再用 `planProtectedHosts`（`scope == ""`）拦截落点主机——
4 个套件的引导机全部是 `scope==""` 的落点角色，
所以「缩掉引导机」这条最致命的路径**已经被通用层拦住**（拍板 ②：直接拦截，不给「先重规划再缩」的出路）。
**所有剩余风险都在成员侧。**

| 套件 | 缩容成员的实际后果 | 级别 | 判据（代码事实） |
|---|---|---|---|
| **rabbitmq** | 被移除节点不做 `forget_cluster_node` ⇒ 以「down 节点」长期留在集群视图；若它是某个 **quorum queue 的 voter**，voter 数下降，缩到失去多数派时该队列**不可用** | 🔴 高 | `scripts/node.sh` 只有 `join_cluster`，无 forget；3.13 默认 classic 队列，但 quorum 由业务显式声明 |
| **rocketmq** | 缩掉 slave ⇒ master 变「无副本」。`brokerRole` 未设 ⇒ ASYNC_MASTER，**不会阻塞写**，但 master 宕机即丢未同步消息；**非 DLedger 无自动切换** | ⚠️ 中 | `configs/broker-master.conf` 无 `brokerRole`（默认 ASYNC_MASTER） |
| **nacos** | 少一个 Nacos 节点；配置/服务数据在 MySQL，**不丢**；存量节点 `NACOS_SERVERS` 仍列着被移除节点，Nacos 标记不健康后继续服务 | ⚠️ 中 | 存储走 MySQL（`SPRING_DATASOURCE_PLATFORM=mysql`），非 JRaft 自持 |
| **powerjob** | Server 无状态（元数据在 MySQL），只减少调度能力 | ✅ 低 | `node.sh` 只注入 JDBC URL 与 akka 端点 |

### 附带两条「扩容」侧缺口（一并列出，是否本轮修见 §7）

- **nacos**：`NACOS_SERVERS` 在部署时按当时的 `__node_ips` **固化到每台主机**。
  扩容时新节点拿到全集，但**存量节点列表不含新节点** ⇒ 集群成员视图不一致（Nacos 的成员集合只来自 `NACOS_SERVERS`）。
  rabbitmq（`join_cluster` 单向加入）、rocketmq（broker 注册到 namesrv）、powerjob（对等 + 共享 DB）**都没有这个问题**。
- **rocketmq**：slave 的 `brokerId="{{__broker_id}}"`，而 `__broker_id` 由引擎按
  `store/stackkit/extra.go:64` 推导为 **`__seq`**（第 2 台起是 **2、3…**，boot 恒 0）——
  **没有 `brokerId=1`**。RocketMQ 经典主从约定同组从库从 1 编号，
  `brokerId=1` 缺位对 HA 与路由的影响**需真机确认**，不宜凭推断下结论。

## 8. 分批计划（不同于 §6 的原建议，按「先修错报、再补能力」重排）

| 批次 | 内容 | 为什么这样排 |

> `docs/kafka套件方案.md` §6 原来的建议是「nacos + rabbitmq 合并一轮 / rocketmq 单独一轮 /
> powerjob 只补探活端点」——
> 与上表一致，只是**把 D1/D2 提到最前**：它们是错误报告，优先级高于能力补全。

## 9. 明确不做

- **nacos 扩容时的成员视图修复**（存量节点重渲染 `NACOS_SERVERS`）：
  需要「扩容后在存量节点上重跑 node.sh」的能力。现有 `scale_out` 阶段脚本机制可以做，
  但要为套件各写一枚 `scale_out` 脚本 + 真机验证；**建议单列一期**。
- **rocketmq 引入 DLedger**：那是架构级变更（真正的自动切换），不是本轮「补全」范围。
- **rabbitmq quorum 队列的 `rabbitmq-queues shrink`**：需先知道队列类型、逐队列操作，
  依赖 Q3 的探活输出先落地；落在 Q2 之后的独立一期。
- **4 套件的离线资产（`AssetProvisioner`）**：镜像仓库参数已可自定义，与 redis 那轮同口径，不做。

## 11. 第一批实施记录（D1 / D2 → M1 / P1 / N4，已完成）

**结论：三个套件的 compose 已收敛为单一 `${HOME_DIR}/compose.yml`，「探活恒假红」与「卸载/缩容不停容器」
同时修好；通用骨架零改动、其余套件零影响（骨架模板基线仍 43636 字符逐字节一致）。**

### 11.1 修法：一个 `compose.yml` + 条件服务

先纠正 §7 M1 里的一处**口径错误**：`${HOME_DIR}/<comp>/compose.yml` 这个形状
**只救探活、不救停服** —— down/purge 的 `<comp>` 白名单是 `api/stack/stack_compose.go:12` 里那 9 个
大数据组件名（hadoop/zookeeper/yarn/spark/flink/hive/hbase/trino），
新套件自己的子目录名（`namesrv` / `broker` / `mysql`）**不在其中**。
所以三个套件都改为**单一 `compose.yml`，首节点专属服务写成条件服务**：

| 套件 | 改动 | 首节点条件服务 | 行数 |
|---|---|---|---|
| rocketmq | `namesrv-compose.yml` + `broker-compose.yml` → `compose.yml` | `namesrv`（仅 `is_bootstrap=true`） | 164 → 177 |
| powerjob | `compose.yml.<seq>` → `compose.yml` | `mysql`（仅首节点且未指定外部库） | 184 → 215 |
| nacos | `mysql-compose.yml` 并入 `compose.yml`（并删掉 `mysql_probe` 占位 + `sed` 删除 hack） | `mysql`（同上） | 231 → 254 |

三处都保留**分段拉起**：先 `up -d mysql` / `up -d namesrv`（等端口就绪、完成库初始化），
再 `up -d 主体服务` —— 同一文件一次性拉起时 MySQL/NameServer 往往尚未就绪。

### 11.2 迁移块（老部署的升级路径，不能省）

### 12.4 两大真机实测发现（apache/rocketmq:4.9.7）与修复

**发现 ①：只配 `brokerId=1` 不配 `brokerRole`，从库仍以 master 启动（双 master 抢注）。**
`broker-slave.conf` 原注释想当然地写着「与 Master 组成主备」，但 RocketMQ 只在 `brokerRole=SLAVE` 时才以从库身份注册。
真机现象：两台 broker 都是 master，同组同名 broker 每 30 秒互相覆盖注册，`clusterList` 始终只剩一行——
**HA 形同虚设，属「部署完成即隐性失效」型缺陷**。修复：`configs/broker-slave.conf` 18 → 22（补 `brokerRole=SLAVE` + 实测注释）。

**发现 ②：镜像内没有 `/home/rocketmq/bin`，注册校验从部署第一天起静默失效。**
`node.sh` 的监督校验用 `sh /home/rocketmq/bin/mqadmin`，而 4.9.7 镜像里 `mqadmin` 只在 `$ROCKETMQ_HOME/bin`；
报错又被 `2>/dev/null || true` 吞掉，`REG_OK` 永远为 0。修复：`scripts/node.sh`（累计 163 → 177，含第一批的 compose 收敛）——
`docker exec … bash -c "sh \$ROCKETMQ_HOME/bin/mqadmin …"`，必须经容器内 bash 展开（宿主机侧展开取不到容器内变量）。

### 18.2 资产条挂载步错位 —— 用户报「没文件也不提示」的根因

用户问：本地没有 `.ez` 时打开「安装延迟队列插件」开关，**资产条完全不出现**（不像大数据会提示），
怀疑「文件是不是存在数据库里」。**结论：与数据库无关，是挂载步错位。**

资产条注册在 `forms.step2Comp`（第 2 步），而触发它的 `delayed_plugin` 是**第 3 步**的共享变量：
第 2 步时开关恒为 `false` ⇒ 组件 `v-if="pluginOn"` 恒假、永不进 DOM；用户走到第 3 步打开开关时，
那条资产条在**上一屏**，因果链永远看不到。大数据 jar 条正常，是因为它的触发控件与资产条在
**同一个**套件组件里（都在第 2 步）。
